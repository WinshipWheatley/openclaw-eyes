# Operator Runtime Fit Audit\n\n## 1. Executive Summary\nOpenClaw currently has a bounded Mission Control request-file service. It classifies approved request files, routes them through deterministic local rails, writes heartbeat/response readbacks, and uses read models/SQLite receipts for selected rails. The LM and worker stages are mostly contract-only, LM-shaped selection, package staging, no-op worker receipts, and review packet lifecycle, not live model or worker execution.\n\n## 2. Current Chain versus Desired Chain\n- The current runtime is not a single linear universal chain; it is a request-family router with separate deterministic rails.\n- The privacy gate exists as hash-only package-queue privacy rows, not a universal dynamic PII gate before every rail.\n- LM1 is not live; it is contract-only/deterministic selection over existing action payloads.\n- The package compiler exists for the workflow-package rail, not every request family.\n- SQLite package truth exists, but only selected rails have SQLite-backed canonical rows.\n- Capability/provider gate exists as dry-run gate rows and registry read models, not a live provider executor.\n- LM2/worker cage is not live; it is child-package gate contracts, package stubs, and review lifecycle.\n- Worker receipts are no-op/offline/rail-specific, not live worker cage receipts.\n- Business-action gates are closed by default; no live executor was found.\n- Dynamic cards are partial and fragmented; a generic card packet is still needed.\n\n## 3. What Exists and is Good\n- Approved-inbox bounded request pickup and duplicate skipping.\n- Fail-closed router behavior when authority_boundary contains true grants.\n- Contextual system-question short-circuit that prevents diagnostic package staging.\n- Workflow package queue storing raw text as protected hashes rather than raw prompt bodies.\n- Capability and business-action gates defaulting to closed.\n- Operator review packet language that separates worker output from speaker authority.\n- Provider selection registry stating provider choice does not grant authority.\n\n## 5. What is Partial (Dry Run / Contract Only)\n- Workflow Composer is planning only and safe_to_execute=false.\n- LM-bounded operator orchestration is contract_only_no_live_lm.\n- Harness provider selection is registry only.\n- Spawned worker package lifecycle is read-model contract only.\n- Worker package staging creates local package stubs only.\n- OpenClaw LM child package gate models child package policy but does not spawn swarms.\n- Operator card render packet contract is non-executing.\n- Business-action gate rows are closed and not an executor.\n\n## 6. What is Missing\n- A universal runtime envelope that makes context, privacy, proof refs, and dynamic card output consistent across all request families.\n- A live LM1 planner; current state is intentionally contract-only/deterministic substitute.\n- A real LM2 worker cage runtime with sandbox, authority checks, receipts, and review.\n- A single generic dynamic card packet emitted by the backend for every operator-visible response.\n- A dedicated universal receipt envelope for package, worker, review, approval, and business-action outcomes.\n- A positive business-action executor gate; current gates are closed and protective.\n- A universal approval-to-execution bridge; current approval records do not execute actions.\n\n## 7. What Should Not Be Built Yet\n- A real LM2 worker cage runtime\n- A live business-action executor gate\n- Universal approval-to-execution bridge\n\n## 8. False Recursive Truth Risks\n**Current Guards:**\n- workflow_package_queue stores protected_text_hash and raw_text_stored=0 for package inputs\n- lm_bounded_operator_orchestration requires selected action to exist in operator_action_payloads\n- system_question_answer answers from local read models and SQLite metadata only\n- evidence_confidence_scoring ranks receipts/hashes/source rows above generated summaries\n- memory_promotion_gate keeps candidate memory separate from truth promotion\n- guardian_output_gate validates response payloads before publication\n\n**Remaining Risks:**\n- Ad hoc response/card fields may make generated summaries look like app truth if not paired with explicit proof refs.\n- Approval records can be mistaken for execution proof unless card copy separates approval, execution, and receipt.\n- LM-shaped recommendation copy can sound authoritative unless safe_to_execute and provider_choice_grants_authority stay visible.\n\n**Rule:** LM output is never truth by itself.\n\n## 9. Minimum Viable Runtime Upgrade Path\n1. Freeze existing request-response, workflow-package, system-question, workroom-review, and workbook-registration behavior with focused regression tests.\n2. Add backend dynamic_card_packet as an additive field beside existing visible_cards/operator_display fields.\n3. Populate dynamic_card_packet for system-question, workflow-package, workroom-review, and workbook-registration rails first.\n4. Add bridge equality and Mac-render smoke tests that compare old card content to new card packets.\n5. Only after dynamic cards are stable, define a universal receipt envelope shared by package, approval, review, and future worker rails.\n6. Keep live LM/worker/business-action activation blocked until privacy, authority, sandbox, receipt, review, and rollback gates are test-backed.\n\n## 10. Recommended Next Three Backend Tasks\n1.
