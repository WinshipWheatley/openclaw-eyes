

# OpenClaw Legal — Pricing and Positioning

## Purpose

This document defines early pricing posture and market positioning for OpenClaw Legal.

It is not a final price sheet. It is a strategic guide for how to talk about value, packaging, and pricing without undercutting the product or overpromising what Version 1 can do.

## Internal draft warning

This is internal buyer-facing preparation, not final external sales material. Do not send to buyers as-is. Create external-facing versions only after the go/no-go gate clears. Verify current implementation before making capability claims. Roadmap concepts such as Connect, adaptive ETA, model distribution, multi-node throughput, OCR, email/portal connectors, and local model review must be labeled as roadmap unless verified built.

Support, rush, data, hardware, backup, and offboarding boundaries are governed by `OPENCLAW_LEGAL_SUPPORT_BOUNDARY.md` before paid pilot or deployment pricing is quoted.

## Positioning statement

OpenClaw Legal is private local discovery infrastructure for law firms that need control, speed, auditability, and predictable cost.

It should be positioned as firm-owned legal operations infrastructure, not as another generic AI subscription.

## Primary value claim

```text
OpenClaw Legal helps your firm move discovery from scattered files and unclear status into a controlled local matter vault with source tracking, local processing, search, review packets, audit trails, and clear processing visibility.
```

## What the firm is paying for

The firm is not just paying for software.

The firm is paying for:

- local privacy and control
- reduced discovery chaos
- source registration and auditability
- faster path from raw files to searchable material
- clearer status for lawyers and staff
- review packet generation
- reduced manual coordination
- predictable infrastructure cost
- controlled updates
- future expansion modules
- the ability to use firm-owned hardware more effectively

## What not to position as the main value

Avoid leading with:

- generic AI chat
- legal advice automation
- attorney replacement
- miracle privilege detection
- full e-discovery replacement
- unlimited file support
- cloud AI analysis
- cheapest possible tool

OpenClaw Legal should be sold on controlled infrastructure, not gimmicks.

## Pricing philosophy

Pricing should reflect operational value and trust, not just file volume.

The product should not copy the exact pain of per-GB cloud e-discovery pricing if the pitch is predictable local cost.

Better pricing posture:

```text
Predictable local discovery infrastructure with modular expansion.
```

Pricing should account for:

- setup complexity
- hardware requirements
- number of users/nodes
- modules installed
- support/update expectations
- practice-area complexity
- volume of discovery handled
- value of privacy/control
- avoided manual labor
- avoided unpredictable SaaS spend

## Strongest early pricing model

The strongest early model is likely:

```text
Setup + local deployment + annual support/updates + optional paid modules.
```

This aligns with:

- firm-owned infrastructure
- controlled local deployment
- ongoing maintenance
- modular roadmap
- predictable cost
- Version 1 reality

## Possible packages

These are positioning packages, not final prices.

### 1. Foundation Deployment

For the first firm or a small firm starting with controlled local discovery workflow.

Includes:

- local Legal Vault setup
- matter workspace workflow
- source registration and hashing
- supported-file local extraction
- search and report workflow
- review packet export
- audit trail
- basic status/queue visibility
- documentation and training

Best for:

- first pilot
- small firm
- focused discovery workflow
- proof of value

### 2. Professional Deployment

For a firm that wants a stronger day-to-day workflow and support.

Includes Foundation plus:

- guided console workflow when available
- stronger queue/ETA visibility
- unsupported-file Alternative Methods workflow
- update manager
- firm profile configuration
- priority support/update plan

Best for:

- discovery-heavy small firm
- firm that wants operational confidence
- firm that needs repeatable workflows

### 3. Private Compute Deployment

For firms that want dedicated local hardware and future multi-node capability.

Includes Professional plus:

- Mac Studio-class Primary Node configuration
- local model setup if approved
- Connect menu / node-readiness planning
- processing capacity planning
- model/update distribution planning
- future worker-node expansion path

Best for:

- high-volume discovery firm
- privacy-conscious firm
- firm wanting fixed local infrastructure rather than cloud meter dependency

### 4. Module Expansion

Optional paid modules added only when the firm chooses them.

Possible modules:

- OCR / scanned PDF module
- email evidence module
- timeline module
- privilege screening candidate module
- discovery connector module
- multi-node processing module
- local model review module
- unsupported-file handler packs

Modules should be versioned, opt-in, and isolated per firm.

## First-firm pricing posture

For the first law firm, pricing may need to balance:

- real value delivered
- early product risk
- implementation labor
- learning value
- relationship value
- future case study/reference value, if allowed
- productization discipline

Do not give away the product as if it has no value.

But do not price it like a fully mature enterprise platform before the first deployment proves itself.

A good posture:

```text
This is a focused first deployment / v1 buildout with clear scope, local privacy, and a productization path. The price reflects setup, customization inside a reusable architecture, and support — not unlimited feature development.
```

## Pricing boundaries

Do not offer unlimited scope.

Do not promise every unsupported file will be handled immediately.

Do not include open-ended support by default.

Do not promise custom work will be free forever.

Do not price in a way that forces every Firm #2 feature into Firm #1 automatically.

Do not make update/support obligations vague.

## Support structure

Support should be defined in tiers or boundaries.

Possible support categories:

### Included support

- installation/configuration help
- basic workflow training
- bug reports
- security/stability updates
- documentation updates

### Paid support / maintenance

- module updates
- new capability requests
- custom connector work
- unsupported file handler development
- additional node setup
- advanced workflow configuration
- periodic system review

### Not included unless contracted

- emergency litigation support
- full manual discovery review
- legal advice
- forensic expert testimony
- unlimited custom development
- remote access to sensitive matter data

## Hardware positioning

Hardware should be positioned as an asset, not a burden. The firm is buying private local discovery infrastructure, not a chatbot.

Message:

```text
Instead of renting every discovery workflow from a cloud meter, the firm can own a powerful local discovery workstation/appliance that processes sensitive matter data under firm control.
```

**Hardware Ladder / Capability Tiers Doctrine** (see `OPENCLAW_LEGAL_GOVERNING_PRINCIPLES.md`):
- Modest hardware proves the workflow; stronger hardware makes heavier local discovery intelligence practical. Hardware tiers affect pricing, support expectations, and capability claims.
- Production hardware is firm-owned and separate from developer-owned reference bench hardware. Avoid "buying the developer a laptop" framing.
- Development/tooling budgets may include developer-owned reference environment costs.
- Capability claims require benchmark validation. Avoid hype or unproven hardware guarantees.

Recommended framing:

- Primary Node: Mac Studio-class machine
- Worker Nodes: approved firm computers
- Lawyer Workstations: assigned-matter devices plus optional idle compute

Do not require multi-node architecture for v1 sale. Present it as an expansion path.

## Per-GB SaaS comparison

Be careful and factual.

Do not claim every SaaS platform is bad.

Positioning:

```text
Large SaaS e-discovery platforms can be powerful, but many small and mid-sized firms need a more predictable, local-first workflow for recurring discovery operations.
```

The comparison should focus on:

- predictable cost
- local data control
- lower workflow overhead
- firm-owned infrastructure
- modular growth
- no default matter-data cloud dependency

Avoid saying:

- “SaaS is insecure”
- “cloud discovery is always bad”
- “we replace every e-discovery platform”

## Pricing metrics to consider

Potential pricing inputs:

- number of firm users
- number of approved nodes
- number of active matters
- modules installed
- hardware included yes/no
- support tier
- update tier
- connector complexity
- expected discovery volume
- local model requirements

Avoid making raw data volume the only pricing metric.

If volume matters, use it for support/capacity planning more than punitive metering.

## Value metrics to show buyer

The system should eventually show value through:

- files processed
- files made searchable
- unsupported files surfaced
- review packets generated
- processing time saved
- ETA accuracy improvements
- time saved from additional nodes
- time saved from model/module updates
- reduced manual rework
- reduced unknown-status discovery batches

These metrics can support renewals and module upgrades.

## Positioning against alternatives

### Against manual workflow

```text
Manual folders may work for small batches, but they do not give a reliable matter vault, processing status, audit trail, unsupported-file workflow, queue, or ETA.
```

### Against cloud storage

```text
Cloud storage stores files. OpenClaw Legal is designed to process and track discovery workflow around those files.
```

### Against SaaS e-discovery

```text
Enterprise e-discovery platforms are powerful. OpenClaw Legal is for firms that want a focused private local workflow with predictable infrastructure and modular expansion.
```

### Against generic AI tools

```text
Generic AI tools can answer questions, but they do not provide a local matter vault, audit-first processing, firm permissions, review packets, update lanes, or controlled unsupported-file handling.
```


```text
The goal is predictable cost and firm control, not a surprise meter every time a discovery batch grows.
```

## First conversation pricing discipline

In an early sales conversation, do not lead with a hard number too fast.

First establish:

- size of firm
- practice area
- discovery pain
- current workflow
- current tools/costs
- privacy concerns
- file types
- volume patterns
- whether hardware is needed
- must-have modules
- support expectations

Then price around the deployment scope.

## Discovery questions for buyer

Ask:

- How do you receive discovery today?
- What file types cause the most pain?
- How often do you receive large batches?
- Where do files live after download?
- Who is responsible for processing them?
- How do lawyers know what has been reviewed?
- Do you currently use cloud e-discovery tools?
- What do those tools cost you?
- Are there privacy or client-data concerns?
- Would a local firm-owned system be attractive?
- Do you already have Mac hardware suitable for a Primary Node?
- Would predictable setup/support/module pricing be preferable to per-GB usage?

```text
OpenClaw Legal Foundation Deployment

- supported-file processing
- search/report/review packet workflow
- audit/status visibility
- documentation/training
```

Then offer add-ons:

- hardware configuration
- advanced support
- custom unsupported-file/module work
- additional firm computers/nodes
- future OCR/email/timeline modules

## Red lines

Do not sell:

- legal advice
- outcome guarantee
- guaranteed privilege decisions
- unlimited custom development
- unlimited file support
- cloud processing without explicit approval
- hidden remote access to matter data
- updates that can change workflow without consent

## Success criteria for pricing model

The pricing model should:

- feel predictable to the firm
- reflect real setup/support labor
- support productization
- fund future module development
- avoid unlimited obligations
- make additional nodes/modules commercially logical
- not punish the firm merely for having large discovery batches
- clearly separate base product from custom work

## Bottom line

OpenClaw Legal should be priced and positioned as private local discovery infrastructure, not as generic AI software.

The first firm should understand that they are buying a controlled local foundation that can grow safely: more file types, more nodes, more modules, and better local models — without losing control of sensitive matter data or having another firm’s workflow break theirs.
