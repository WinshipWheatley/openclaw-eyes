# OpenClaw Legal First Pilot Scope

## 1. Purpose

This document defines the smallest safe shape for a conditional first paid OpenClaw Legal pilot.

It is not a general release plan. It is not proof of real deployment readiness. It is not buyer-facing sales copy as-is. It is an internal scope package for deciding whether a first paid pilot can be written, priced, and supported without turning OpenClaw Legal into emergency legal-operations support or open-ended custom work.

This scope assumes the current Legal Console checkpoint remains limited: Phase 2F-B synthetic write is complete, Phase 2G-S synthetic-only GUI Run exists for proof only, real-matter Run is blocked, Reset is explicitly deferred, and feature work should stay bounded to proof/planning unless a new slice is separately approved.

## 2. Pilot verdict

- internal development: Go
- synthetic/public demo: Go
- paid first pilot: Conditional Go
- real deployment: No-Go until separately proven

This verdict means OpenClaw Legal may keep moving through bounded development and synthetic/public-safe demo validation. A paid first pilot may be discussed only if the buyer accepts the written scope, file-type limits, support boundary, attorney-review boundary, hardware/data responsibilities, and no-go stop conditions in this package.

Real deployment remains blocked until support, liability, data, hardware, backup, update, offboarding, and real-matter operating terms are separately proven and written.

## 3. Narrow pilot offer

The first pilot offer is bounded local discovery infrastructure for:

- one firm
- one scoped workflow
- one primary machine
- one local matter vault
- known supported file types only
- a written setup and support window

The pilot should prove whether a small law-office workflow can move from messy local files to tracked, searchable, packet-ready local artifacts while preserving matter boundaries and attorney review.

The pilot is not a firm-wide platform rollout, not a full e-discovery replacement, not a managed litigation-support service, and not approval to broaden GUI controls.

## 4. Included

The first pilot may include only current or near-current safe scope:

- Setup and configuration of a local-first workflow.
- Supported-file intake for agreed file types only.
- Matter vault and source registration workflow.
- SHA-256 hashing and source tracking.
- Local extraction where already supported.
- Local search where already supported.
- Markdown report generation where already supported.
- Review packet export where already supported.
- Sanitized support packet concept and workflow explanation.
- Alternative Methods metadata for unsupported, failed, or no-text sources.
- Synthetic demo validation before buyer reliance.
- Basic onboarding and workflow training.
- Bounded support window for the written pilot scope.
- Review of sanitized diagnostics only, not raw matter files by default.

Everything included must be described as built, prototype-only, or roadmap-only before a buyer sees it.

## 5. Explicitly excluded

The first pilot excludes by default:

- Legal advice.
- Legal conclusions.
- Privilege decisions.
- Attorney replacement.
- Emergency or court-deadline support.
- Raw matter remote review by Winship.
- Broad custom development.
- Unlimited support.
- Support for every file type.
- Connect or distributed workers.
- Queue or ETA behavior.
- Model distribution.
- Timeline candidates.
- Contradiction candidates.
- Privilege screening.
- Email, cloud, or portal connectors.
- Production installer or update manager unless separately approved.
- Run/Reset GUI behavior unless separately planned and approved.
- Full firm IT support.
- Guaranteed search completeness or legal outcome.

Any exception must be written, paid, narrow, and separately approved before work starts.

## 6. Allowed first-pilot file types

Allowed first-pilot file types should be conservative and written into the pilot scope:

- `.txt`
- `.md`
- text-layer `.pdf`
- `.png`, `.jpg`, and `.jpeg` only as a local Tesseract-backed prototype where Tesseract is installed and verified

Excluded unless separately quoted, tested, and approved:

- scanned-PDF OCR
- video
- audio
- email archives
- phone dumps
- proprietary exports
- broad media processing
- unsupported binary or container formats
- any file type requiring cloud tools by default

Unsupported, failed, or no-text files should flow through Alternative Methods metadata and paid custom-scope decisions, not emergency support promises.

## 7. Support boundary

Included support may cover:

- Setup help for the agreed environment.
- Basic workflow training.
- Bug reports for supported built scope.
- Documentation corrections for the agreed workflow.
- Clarification of supported versus unsupported workflow states.
- Review of sanitized diagnostics.

Paid add-on or custom quote support may cover:

- Custom handler work.
- Additional file types.
- Extra training.
- Extra node setup.
- Advanced workflow configuration.
- Custom report shaping.
- Periodic system review.
- Rush support only if explicitly offered and priced.

Never included by default:

- Emergency litigation support.
- Raw matter review by Winship.
- Unlimited custom work.
- Legal strategy.
- Legal advice.
- Privilege review.
- Guaranteed outcomes.
- Full manual discovery review.
- Forensic expert testimony.
- General firm IT support.
- Taking responsibility for litigation deadlines.

If a support issue appears to require raw matter access, pause and seek a safer diagnostic path, public analog, sanitized support artifact, or a written exception.

## 8. Buyer responsibilities

The buyer must accept these responsibilities before a paid pilot:

- The firm owns matter data, source files, outputs, reports, review packets, and matter work product.
- The firm owns or funds production hardware unless a separate written agreement says otherwise.
- The firm handles backups, retention, restore testing, and offboarding unless separately contracted.
- Firm attorneys review outputs before relying on them.
- The firm accepts that OpenClaw Legal is not legal advice and does not replace attorney judgment.
- The firm accepts unsupported-file limits and paid custom-handler boundaries.
- The firm accepts local-only/data-residency rules for real matter workflows.
- The firm does not send raw matter data to non-local tools through OpenClaw Legal by default.
- The firm acknowledges that roadmap modules are not included unless separately built, proven, and contracted.

## 9. Proof required before pilot

Before a paid pilot is offered or accepted, these proof items must be complete or written into a pre-pilot gate:

- Synthetic demo validation completed.
- Support boundary reviewed with the buyer.
- Supported file types agreed in writing.
- No-go items acknowledged in writing.
- Payment, scope, and support terms written.
- Hardware responsibility written.
- Data ownership and data residency terms written.
- Backup, retention, restore, and offboarding responsibilities written.
- Attorney-review and no-legal-advice boundary written.
- Unsupported-file handling policy written.
- Sanitized diagnostics/support packet boundary written.

If these proof items are not ready, the work remains internal development or synthetic/public demo, not a paid first pilot.

## 10. Pilot stop conditions

Stop or decline the pilot if any of these are true:

- The buyer needs emergency support.
- The buyer needs unsupported critical file types immediately.
- The buyer wants remote raw-matter review by Winship.
- The buyer wants legal conclusions.
- The buyer wants privilege decisions.
- The buyer refuses hardware responsibility.
- The buyer refuses data, backup, retention, or offboarding responsibility.
- The buyer expects Connect, queue, ETA, or full e-discovery replacement behavior.
- The buyer will not accept attorney-review and no-legal-advice boundaries.
- The buyer wants open-ended custom development for a narrow setup fee.
- The buyer treats roadmap modules as included deliverables.
- The buyer expects routine support to include litigation-deadline responsibility.

Any single stop condition is enough to halt until the scope is rewritten or the buyer expectation changes.

## 11. Pricing posture

This document does not set final prices.

Pricing should use a structure that prevents cheap open-ended support:

- setup fee
- annual support/update plan
- paid modules
- paid custom handlers
- paid extra training or configuration
- premium rush support only if ever offered

Do not price the first pilot as unlimited access, unlimited file-type support, unlimited custom development, or emergency litigation coverage.

The correct posture is a focused first deployment or v1 buildout with clear scope, local privacy, reusable product architecture, paid support, and explicit limits.

## 12. Next-step rule

After this document, do not build features automatically.

Use this package for a planning session, buyer-readiness review, or written pilot-scope drafting. Any new implementation slice still needs its own scoped plan, proof commands, and approval. `Run Synthetic Dry Run` is allowed only under the synthetic demo validation package, fixed synthetic fixture values, and sanitized status-only output; changes to that control, Real-matter GUI Run, Reset, arbitrary bridge execution, real matter through the app, file pickers, Connect, queue/ETA, OCR/model distribution, unsupported-file feature expansion, cloud/external model processing, or raw matter support remain out of scope unless separately planned and approved.
