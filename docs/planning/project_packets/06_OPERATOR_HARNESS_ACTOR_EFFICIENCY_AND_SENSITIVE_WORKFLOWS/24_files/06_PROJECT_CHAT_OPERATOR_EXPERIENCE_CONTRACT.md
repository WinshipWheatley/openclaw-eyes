## Autodidact / Mastery-to-Assets Doctrine

The operator may function as an autodidact: curiosity-driven rapid learning, mastery, then reduced interest once the challenge is solved. This creates creative/social value but business risk if mastery is not converted into assets, income, products, invoices, documentation, delegated systems, or public-good outputs.

System doctrine:

- Mastery should produce assets.
- Assets should produce income.
- Income should buy freedom.
- Freedom should fund impact.

Project chats should make extraction visible without making the operator manage the machinery. When a lane is mastered, the chat should ask what durable asset, invoice, product surface, delegation path, documentation, or public-good output captures the value.

## Repo Implementation Pointers

None required for ordinary chat orchestration. When a lane requires proof, use exact repo files named by the governing rail, not broad preload.

## Valid Future Lane Moves

- Produce exact Codex/Gemini prompts with allowed paths, forbidden surfaces, validation, and report requirements.
- Recommend a fresh chat or handoff update when context is heavy.
- Translate a future lane into one right-sized stride rather than tiny crumbs.
- Ask for operator review only at real authority boundaries.

## Forbidden Drift

- Do not make the operator speak machine-contract language.
- Do not pass rough gist to coding agents without boundaries.
- Do not hide uncertainty.
- Do not make handoffs emotional summaries without paths, gates, receipts, and stop conditions.
- Do not turn the handoff into the roadmap.

## Review Boundary

Review when prompts become bloated, Codex/Gemini repeatedly miss scope, or the operator has to carry too much context manually.

## Why It Should Last 10-20 Moves

Operator experience doctrine is reusable across all Packet 06 lanes. It should help chats move faster without becoming sloppy.
