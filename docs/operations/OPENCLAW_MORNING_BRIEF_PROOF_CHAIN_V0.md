# Morning Brief Proof Chain v0

**Status:** Docs-Only Planning  
**Date:** 2026-05-10  
**Authority:** Architectural guidance for deterministic evidence-based reporting.

## 1. Purpose
Morning briefs in OpenClaw must be built from a deterministic "proof/report" chain rather than hallucinated from chat memory or speculative agent observations. By grounding the brief in hard evidence (ledger receipts and subsystem reports), the system ensures that the operator is informed by reality, not intuition.

## 2. Layer Order (The Proof Chain)
The brief is synthesized in the following order, with each layer consuming and filtering the layers beneath it:

1.  **Subsystem Proof Receipts (Lowest Level):** Raw deterministic receipts from the ledger (`test_proof_receipt` events). These provide pass/fail signals and execution metadata (exit codes, hashes).
2.  **Subsystem Machine-Contract Reports:** High-signal technical summaries generated by subsystem scripts (e.g., `generate_operator_status.py --check`). These interpret the raw receipts into technical status.
3.  **Guardian Deterministic Security/Readiness Report:** A safety-first audit layer. It checks for permission drifts, exposed secrets (metadata check), and overall system integrity before reporting.
4.  **Hermes Systems-Engineering Improvement Report:** A coherence-tuning layer. It identifies stale docs, dependency bloat, and architectural drift based on the lower reports.
5.  **Chief Synthesis and Prioritization:** The management layer. It gathers all reports, reconciles conflicting signals, and identifies the "Top 3" priorities for the operator based on the day's goals.
6.  **Cassandra Tasteful Human-Readable Report (Highest Level):** The final communication layer. It translates the Chief's synthesis into a concise, low-stress, high-signal brief for the human operator.

## 3. What Test/Proof Receipts Provide
Proof receipts stored in the `business_ops_ledger` provide the deterministic bedrock:
- **Command Label:** The specific check or test that was run.
- **Pass/Fail:** Clear binary signal.
- **Commit:** The Git SHA at the time of execution.
- **Dirty/Clean State:** Whether uncommitted changes were present.
- **Timestamp:** Exactly when the proof was generated.
- **Bounded Output/Hash:** A truncated snapshot of the failure or a hash of the output for integrity verification.
- **Isolation:** Evidence for a specific domain only (no "whole-system" guarantees).

## 4. What Proof Receipts Do NOT Provide
To maintain safety, the system must not infer the following from receipts alone:
- **Live Runtime Health:** A passed test at 9:00 AM does not guarantee the service is running at 10:00 AM.
- **Full Security Posture:** A "clean" secrets check does not mean the system is un-hackable.
- **File/Network/Device Awareness:** Unless the specific command was a network probe, no network status is implied.
- **Permission to Act:** Proof of a fix does not grant the agent permission to deploy or delete without an explicit Directive.
- **Evidence of Correctness beyond the command run:** If the test suite is shallow, the proof is shallow.

## 5. Future Morning Brief SQLite/Read-Model Needs
To support this chain, the system will eventually need to query:
- **Latest Proof Receipts by Label:** What is the current "State of the Union" for each subsystem?
- **Failed Proof Receipts since last brief:** What broke since yesterday?
- **Stale/Missing Proofs:** Which expected daily checks haven't been run?
- **Proof Coverage:** Which areas of the system are currently "dark" (no receipts)?
- **Guardian Escalation Markers:** Did any safety checks trigger a hard-stop?
- **Chief Action Queue:** Which failing proofs require a manual "Fix" directive?
- **Cassandra Inputs:** A structured JSON object containing the above for final rendering.

## 6. Safety & Boundaries
- **Machine-Contract Priority:** Technical reports must remain upstream of human summaries to prevent "smoothing over" critical failures.
- **No Hidden Authority:** The brief does not grant permissions. It only reports status and suggests actions.
- **No Silent Expansion:** New proof categories must be explicitly defined in the taxonomy before they can appear in the brief.
- **Grounded Claims:** The system must never claim "System is Healthy" unless every required proof receipt for that claim is present and passing.

## 7. Non-Goals (Out of Scope for v0)
- **Scheduling:** No cron-jobs or automated timers.
- **Autonomous Runner:** No system to automatically run the tests to "fill" the brief.
- **Guardian/Chief/Cassandra Implementation:** This document defines the *data flow* and *contract*, not the code for these agents.
- **Runtime Probing:** No live hardware or network inspection logic.
